Create a single migration file with the following sections, wrapped in a transaction (begin/commit):

**1. Extend profiles table:**
- Add `unit_preference text check (unit_preference in ('metric', 'imperial')) default 'imperial'` column

**2. Extend recipes table:**
- Add `rating_average numeric(2,1)` column (nullable, null = no ratings yet)
- Add `rating_count int not null default 0` column

**3. Create recipe_comments table:**
```sql
create table recipe_comments (
  id uuid primary key default gen_random_uuid(),
  recipe_id uuid not null references recipes(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  parent_comment_id uuid references recipe_comments(id) on delete cascade,
  content text not null,
  is_edited boolean not null default false,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```
- Add indexes on recipe_id, parent_comment_id, user_id
- Add set_updated_at trigger (reuse existing function from Phase 1)

**4. Create recipe_ratings table:**
```sql
create table recipe_ratings (
  recipe_id uuid not null references recipes(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  rating numeric(2,1) not null check (rating >= 0.5 and rating <= 5 and (rating * 2)::int = (rating * 2)),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  primary key (recipe_id, user_id)
);
```
Note: The check constraint ensures 0.5 increments (0.5, 1.0, 1.5, ... 5.0). Minimum is 0.5 (not 0 — a rating of 0 is meaningless, users who don't want to rate simply don't submit).
- Add index on recipe_id
- Add set_updated_at trigger

**5. Enable RLS on both tables:**

**recipe_comments RLS:**
- SELECT: User can read if they can access the recipe (EXISTS subquery checking recipes.visibility = 'public' OR owner_user_id = auth.uid() OR (visibility = 'family' AND is_family_member))
- INSERT: user_id = auth.uid() AND recipe is accessible (same EXISTS pattern)
- UPDATE: user_id = auth.uid() (own comments only). WITH CHECK ensures user_id stays the same and sets is_edited = true is handled by application layer.
- DELETE: user_id = auth.uid() OR recipe owner (owner_user_id = auth.uid()) OR family admin (is_family_admin). Per locked decision: "comment author can delete their own; recipe owner and family admin can both moderate/delete any comment."

**recipe_ratings RLS:**
- SELECT: User can read if they can access the recipe (same EXISTS pattern as comments)
- INSERT: user_id = auth.uid() AND recipe is accessible
- UPDATE: user_id = auth.uid() (own rating only)
- DELETE: user_id = auth.uid() (own rating only)

**6. Create get_recipe_comments function:**
Use SECURITY DEFINER (per research recommendation to avoid recursive RLS performance issues). First validates the caller can access the recipe, then fetches with recursive CTE. Returns: id, recipe_id, user_id, parent_comment_id, content, is_edited, created_at, updated_at, depth (int), path (text for ordering). Order by path for threaded display. Set search_path = public for security.

**7. Create rating aggregate trigger:**
```sql
create or replace function update_recipe_rating()
returns trigger language plpgsql as $$
begin
  -- Handle both INSERT/UPDATE (NEW) and DELETE (OLD)
  if TG_OP = 'DELETE' then
    update recipes set
      rating_average = (select round(avg(rating), 1) from recipe_ratings where recipe_id = old.recipe_id),
      rating_count = (select count(*) from recipe_ratings where recipe_id = old.recipe_id)
    where id = old.recipe_id;
    return old;
  else
    update recipes set
      rating_average = (select round(avg(rating), 1) from recipe_ratings where recipe_id = new.recipe_id),
      rating_count = (select count(*) from recipe_ratings where recipe_id = new.recipe_id)
    where id = new.recipe_id;
    return new;
  end if;
end;
$$;
```
Create trigger AFTER INSERT OR UPDATE OR DELETE on recipe_ratings FOR EACH ROW.

Important: Use `if not exists` or `drop/create` patterns where appropriate to make migration idempotent. Follow the same style as existing migrations (e.g., 20260203090000_phase1_foundation.sql).

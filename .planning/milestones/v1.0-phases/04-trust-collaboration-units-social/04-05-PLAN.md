**src/features/recipes/types.ts — Extend RecipeIngredient:**
Add optional canonical fields to the existing RecipeIngredient type. This is backward-compatible since existing ingredients stored as JSONB will just have these fields as undefined.

```typescript
export type RecipeIngredient = {
  text: string;
  sort_order: number;
  // Phase 4: canonical unit fields (optional for backward compat)
  amount?: number | null;
  unit?: string | null;
  original_text?: string | null;
  is_ambiguous?: boolean;
};
```

**app/recipes/[id].tsx — Unit-converted ingredient display:**
Import `displayAmount`, `canConvert` from `@/features/units/conversions` and `getUnitPreference` from `@/features/units/api`. Import `UnitSystem` from `@/features/units/types`.

Add state for unitPreference (default 'imperial'). Load preference on mount (after session is available) via getUnitPreference().

Update the ingredients rendering section. For each ingredient:
1. If ingredient has `amount` and `unit` and `!is_ambiguous`: call `displayAmount(amount, unit, preference, original_text || text)` to get the converted display string, then append the ingredient name portion
2. If ingredient has `is_ambiguous === true`: show `text` as-is with a subtle indicator — a small info icon or dim "(approx.)" text. Per locked decision: "preserved as-is with a subtle indicator that conversion wasn't possible"
3. If ingredient has no canonical fields (legacy data or no unit): show `text` unchanged

Display format per locked decision: "2 cups (500ml) flour" — the `displayAmount` function from Plan 02 handles this format.

**app/recipes/create.tsx — Parse+confirm on ingredient entry:**
Import `parseIngredient` from `@/features/units/parser`.

When user adds/edits an ingredient text field, after they finish typing (on blur or on a "Parse" button tap):
1. Call `parseIngredient(ingredientText)` to get parsed result
2. Show a preview below the input: "Parsed: {amount} {unit} of {ingredient}" if successfully parsed
3. If ambiguous, show: "Ambiguous measurement — will be preserved as-is"
4. Show a "Confirm" button to accept the parse and store canonical fields, or user can ignore and just keep the raw text
5. When confirmed, update the ingredient object to include `amount`, `unit`, `original_text`, `is_ambiguous` fields
6. When not confirmed (user ignores or dismisses), store ingredient with just `text` and `sort_order` (backward compat)

Implementation approach:
- Add a `parsedPreview` state per ingredient (or track in the ingredients array)
- Parse on blur of ingredient text input (auto-parse)
- Show preview inline below the ingredient input
- Confirm button stores canonical fields into the ingredient object
- The existing form submit already sends ingredients array to createRecipe — the JSONB column will store the extra fields automatically

**app/recipes/[id]/edit.tsx — Same parse+confirm flow:**
Apply the same parse+confirm pattern as create.tsx. When loading existing ingredients:
- If ingredient already has canonical fields (amount, unit), show them as pre-parsed
- If ingredient has no canonical fields (legacy data), show "Not yet parsed" with option to parse
- Allow re-parsing any ingredient by editing the text

Keep the UX lightweight — parsing is automatic on blur, confirmation is a single tap. Per locked decision: "Parse + confirm approach: when ingredients are entered (manual or scan), show the parsed canonical result and let the user confirm or correct before saving. Best-effort parsing into canonical form, but user has final say."

Important: Do NOT break existing recipe creation/editing. All new fields are optional in the type and in storage. Recipes created without parsing still work fine.
